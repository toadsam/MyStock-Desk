# 배포 후 점검 기록

2026-11-10, `mywave.day`로 공개한 날 한 점검과 수정을 적었습니다. 무엇이 문제였고, 왜 생겼고, 어떻게 고쳤고, 고쳐졌다는 걸 무엇으로 확인했는지를 남기는 것이 목표입니다.

점검과 수정은 AI 코딩 도구(Claude Code)와 함께 했습니다. 어디까지를 AI가 하고 어디를 사람이 정했는지도 같이 적습니다.

## 한눈에

| | 점검 전 | 수정 후 |
|---|---|---|
| API 검사 152개 중 통과 | 137 | 146 |
| 백엔드 테스트 | 29개 | 41개 (12개 추가) |
| 공개 데모 계정 | 누구나 비밀번호를 바꿀 수 있음 | 프로필과 비밀번호 잠금 |
| 로그아웃한 토큰 | 24시간 동안 계속 통함 | 즉시 무효 |
| 오류 문구 | `Request failed with status code 400` | 서버가 적은 한글 문장 |

남은 6개는 없는 기록에 404 대신 400을 주는 상태 코드 관례입니다. 동작에는 문제가 없어 이번 범위에서 뺐습니다([아직 남은 것](#아직-남은-것)).

## 어떻게 점검했나

"기능이 잘 작동하는지 테스트해 달라"는 요청 하나로 시작했습니다. AI가 세 가지 방법을 섞어 진행했습니다.

1. **API 전수 검사.** 컨트롤러와 요청 DTO를 읽고 검사 스크립트를 썼습니다. 새 계정을 만들어 조회 주소 56개를 전부 부르고, 목표·지출·계좌·예산·매매·메모·관심종목을 만들고 고치고 지웠습니다. 여기에 "막혀야 하는 요청"을 섞었습니다. 음수 금액, 99조 원, 미래 날짜, 2만 자 메시지, 남의 기록 수정, 로그아웃한 토큰 같은 것들입니다. 152개 중 15개가 걸렸습니다.
2. **화면 조작.** 브라우저를 직접 눌러 데모 로그인, 빠른 기록, 직접 입력, 삭제 확인, 목표 생성, 코치 대화, 검색, 종목 상세를 확인했습니다. 데스크톱과 모바일 크기를 모두 봤고 콘솔 오류는 없었습니다.
3. **운영 사이트 확인.** 쓰기 테스트는 로컬(H2)에서만 했습니다. 공개 데모 계정에 테스트 데이터를 남기지 않기 위해서입니다. 운영에서는 읽기와 "거절되는 요청"만 보냈습니다.

걸린 항목은 코드를 열어 원인을 확인한 뒤에 문제로 적었습니다. 예를 들어 "로그아웃 뒤에도 토큰이 통한다"는 `AuthController.logout()`이 아무 일도 하지 않는 빈 메서드인 것을 확인하고 나서 확정했습니다.

## 문제와 해결

### 1. 데모 계정을 누구나 망가뜨릴 수 있었다

- **증상.** 로그인 화면의 "데모 계정으로 로그인"으로 들어온 사람이 비밀번호나 이메일을 바꿀 수 있었습니다. 한 번 바뀌면 그 뒤로 데모 로그인이 전부 실패합니다.
- **원인.** 데모 계정도 보통 계정과 똑같이 취급했습니다. 혼자 쓰던 때의 구조가 공개 뒤에도 그대로였습니다.
- **해결.** [`DemoAccountPolicy`](../backend/src/main/java/com/stockflow/member/service/DemoAccountPolicy.java)를 두고 데모 계정의 프로필 수정과 비밀번호 변경을 403으로 막았습니다. 지출이나 목표 같은 기록은 써 보라고 둔 것이라 막지 않습니다.
- **확인.** 운영에서 데모 계정으로 두 요청을 보내 403과 안내 문구를 받았습니다.

### 2. 로그아웃해도 토큰이 살아 있었다

- **증상.** 로그아웃한 뒤에도, 비밀번호를 바꾼 뒤에도 예전 토큰으로 API가 그대로 불렸습니다. 만료까지 24시간입니다.
- **원인.** JWT는 서버가 기억하지 않는 표라서, 서버가 "이 토큰은 끝났다"를 알 방법이 없었습니다. 로그아웃은 프론트가 토큰을 지우는 것뿐이었습니다.
- **해결.** 두 가지를 나눠 처리했습니다.
  - 로그아웃: 토큰마다 번호(`jti`)를 넣고, 로그아웃하면 그 번호를 `revoked_token`에 적어 요청마다 대조합니다. 계정 전체가 아니라 **그 토큰 한 장만** 버립니다. 데모 계정은 여럿이 같이 쓰므로, 한 사람의 로그아웃이 나머지를 내보내면 안 되기 때문입니다.
  - 비밀번호 변경: `member.tokens_valid_from`을 지금으로 당겨 그 전에 발급된 토큰을 모두 버립니다. 화면은 안내 문구와 함께 로그인으로 보냅니다.
- **확인.** [`AccountSafetyIntegrationTest`](../backend/src/test/java/com/stockflow/auth/AccountSafetyIntegrationTest.java). 같은 계정으로 두 번 로그인해 하나만 로그아웃하고, 그 하나만 401이 되는지 봅니다.
- **대가.** 요청마다 DB 조회가 두 번 늘었습니다. 지금 규모에서는 문제가 없고, 커지면 캐시를 둘 자리입니다. 번호가 없는 예전 토큰은 받지 않게 해서 배포 직후 기존 로그인이 한 번 풀렸습니다.

### 3. 멤버십 등급을 스스로 올릴 수 있었다

- **증상.** `PATCH /api/members/me/membership`에 `VIP`를 보내면 그대로 적용됐습니다.
- **원인.** 결제가 없는데 등급을 바꾸는 주소만 남아 있었습니다. 화면에서는 쓰지 않던 주소입니다.
- **해결.** 주소를 없앴습니다. 권한을 붙여 고치는 것보다, 쓰지 않는 기능을 지우는 쪽이 맞다고 봤습니다.

### 4. 말이 안 되는 숫자와 날짜가 저장됐다

- **증상.** 99조 원짜리 지출이 저장돼 월 합계가 통째로 틀어졌습니다. 미래 날짜의 지출과 매매, 과거 날짜의 목표, 음수 모은 금액(달성률 -10%), 음수 예산, 500% 절감률, 2만 자 코치 질문도 통과했습니다.
- **원인.** 요청 DTO에 `@NotNull`, `@Positive` 정도만 있고 상한이 없었습니다. 예산, 시뮬레이션, 퀵버튼 기록, 관심종목 메모 주소는 `@Valid` 자체가 빠져 있었습니다.
- **해결.**
  - 금액 상한을 [`Limits`](../backend/src/main/java/com/stockflow/global/validation/Limits.java) 한 곳에 모았습니다. 지출 1억, 목표·예산·단가 100억, 잔액 ±1조.
  - 날짜는 애너테이션이 아니라 서비스에서 봅니다. "오늘"이 서울 날짜여야 하고([계산 규칙](RULES.md)), 테스트가 시계를 바꿔 끼우기 때문입니다.
  - 목표 날짜는 **새로 과거로 옮길 때만** 막습니다. 이미 날짜가 지난 목표를 완료로 바꾸는 건 되어야 합니다. 처음에는 DTO에 `@FutureOrPresent`를 붙이려 했는데, 그러면 지난 목표의 상태 버튼이 전부 막힙니다.
- **확인.** [`InputLimitsIntegrationTest`](../backend/src/test/java/com/stockflow/global/InputLimitsIntegrationTest.java). 운영에서도 같은 요청 다섯 개가 400과 한글 문구로 거절되는 것을 봤습니다.

### 5. 고치다가 찾은 것

수정한 내용을 화면에서 확인하다가 원래 있던 문제 세 개가 더 나왔습니다.

- **오류 문구가 영어 그대로 떴습니다.** 데모 계정 잠금을 화면에서 눌러 보니 안내 문구 대신 `Request failed with status code 403`이 나왔습니다. 4xx 응답은 axios가 예외로 던지는데, [`myWaveApi.ts`](../frontend/src/mywave/myWaveApi.ts)의 `unwrap`이 그걸 받지 않고 있었습니다. 이번에 새로 생긴 문제가 아니라 모든 화면의 모든 오류가 그랬습니다. API 검사만으로는 보이지 않고 화면을 눌러 봐야 보이는 종류였습니다.
- **없는 주소가 500이었습니다.** 멤버십 주소를 지우고 불러 보니 404가 아니라 500이 나왔습니다. 맨 아래의 `Exception` 처리기가 전부 받아 가고 있었습니다. 404와 405 처리기를 따로 뒀습니다.
- **날짜가 박힌 테스트가 깨질 상태였습니다.** 목표 테스트가 `2026-09-30`을 고정으로 쓰고 있었습니다. 지금까지는 과거 날짜도 저장돼서 통과했고, 날짜 검증을 넣자마자 실패했습니다. 오늘 기준 상대 날짜로 바꿨습니다.

## AI를 어떻게 썼나

**AI가 한 일**

- 컨트롤러와 DTO를 읽고 검사 152개를 설계하고 스크립트로 만들었습니다. 정상 동작만이 아니라 막혀야 하는 요청을 같이 넣은 것이 문제를 찾은 이유입니다.
- 걸린 항목마다 코드에서 원인을 찾아 근거와 함께 보고했습니다.
- 수정안을 만들고, 테스트를 쓰고, 로컬과 운영에서 확인했습니다.
- 자기가 고친 것을 화면에서 다시 눌러 보다가 5번의 세 문제를 스스로 찾았습니다.

**사람이 정한 일**

- 무엇부터 고칠지. 디자인 지적과 구글 로그인 요청도 같이 있었는데, 공개된 주소에서 바로 터질 수 있는 계정 문제를 먼저 하기로 했습니다.
- 어디까지 고칠지. 상태 코드 관례는 이번에 손대지 않기로 했습니다.
- 운영에 올릴지. 커밋과 푸시는 매번 확인을 받고 진행했습니다.

**해 보고 알게 된 점**

- "테스트해 줘" 한마디가 통한 건, 통과 여부를 숫자로 돌려받았기 때문입니다. 137에서 146이 된 것을 같은 스크립트로 다시 돌려 확인했습니다. AI에게 일을 시킬 때는 끝났다는 말이 아니라 다시 돌릴 수 있는 검사를 받아야 합니다.
- AI가 찾은 문제를 그대로 믿지 않았습니다. 15개 중 6개는 버그가 아니라 관례 차이였습니다. 걸린 항목을 "실제 문제"와 "기대가 달랐던 것"으로 나누는 판단이 필요했습니다.
- 운영 데이터를 건드리지 않게 선을 그어 줘야 했습니다. 쓰기는 로컬에서만, 운영은 읽기와 거절되는 요청만.

## 아직 남은 것

- **상태 코드.** 없는 기록과 남의 기록에 400을 줍니다. 404와 403이 맞습니다. 남의 기록을 실제로 건드릴 수는 없습니다.
- **데모 데이터가 낡습니다.** 시드가 서버를 처음 띄운 날 기준이라, 날이 갈수록 홈이 비어 보입니다. 데모 계정에 누가 이상한 기록을 남겨도 지워지지 않습니다. 주기적으로 다시 채우는 장치가 필요합니다.
- **총 자산 숫자가 화면마다 다릅니다.** 투자 자산, 투자와 현금, 계좌까지 합친 값이 비슷한 이름으로 나옵니다.
- **쓰지 않는 파일.** `MemberMembershipRequest.java`는 주소를 지우면서 쓰는 곳이 없어졌습니다.

## 같은 날: 도메인 연결

`mywave.day`를 Cloudflare에서 사서 Railway의 `frontend` 서비스에 붙였습니다. 걸린 곳 두 가지만 적습니다.

- **루트 도메인에는 원래 CNAME을 못 씁니다.** Cloudflare가 이를 자동으로 풀어 줘서 `@`에 CNAME을 그대로 넣었습니다. 다른 등록 업체였다면 네임서버를 옮겨야 했습니다.
- **프록시는 꺼야 합니다.** CNAME을 회색 구름(DNS only)으로 둬야 Railway가 인증서를 직접 발급합니다. 주황 구름으로 두면 발급이 막힙니다.

레코드는 도메인마다 둘입니다. 트래픽용 CNAME과 소유 확인용 `_railway-verify` TXT. `www`에도 같은 식으로 넣었습니다.
